# DbsPulse — سامانه ارزیابی عملکرد سازمانی

سامانه‌ای برای مدیریت فرآیند **ارزیابی عملکرد پرسنل پیش از تمدید قرارداد**، با یک زنجیرهٔ تأیید چهارمرحله‌ای، گزارش‌گیری تحلیلی برای منابع انسانی و خروجی رسمی قابل چاپ/PDF با قابلیت تأیید اصالت.

زنجیرهٔ تأیید:

```
مسئول واحد ← منابع انسانی ← معاونت ← مدیرعامل ← نهایی‌شده
```

---

## قابلیت‌ها

### گردش‌کار ارزیابی

- **زنجیرهٔ تأیید چهارمرحله‌ای** با ماشین حالت اعلانی؛ هر گذار فقط برای نقش و شخص مجاز و در ترتیب درست امکان‌پذیر است.
- **مسیر ویژهٔ «مدیر»:** برای پرسنلِ علامت‌خورده به‌عنوان مدیر، معاونت خودش نمره‌دهندهٔ اول است و مرحلهٔ مسئول واحد حذف می‌شود.
- **برگشت پرونده:** هر تأییدکننده می‌تواند پرونده را با ذکر دلیل یک مرحله به عقب بازگرداند؛ امتیازهای قبلی حفظ و دلیل به‌صورت کامنت + رویداد audit ثبت می‌شود.
- **کامنت و پاسخِ رشته‌ای** روی پرونده در هر مرحله، به‌همراه اعلان درون‌برنامه‌ای برای طرف مقابل.
- **قانون شواهد عینی:** برای امتیازهای ۱ و ۵ ثبت شواهد اجباری است (حداقل ۳ و حداکثر ۴۰ کلمه)؛ این قانون سمت سرور اعمال می‌شود.

### گزارش‌گیری منابع انسانی

- **داشبورد تحلیلی** با کارت‌های خلاصه، قیف گردش‌کار و نمودار میانگین امتیاز به‌تفکیک واحد.
- **گزارش‌های فیلترشونده:** میانگین به‌تفکیک واحد، میانگین هر شاخص، ریز یک شاخص خاص به‌تفکیک واحد، و مقایسهٔ امتیاز فرد با میانگین واحدش.
- **فیلترهای ترکیب‌پذیر:** دورهٔ ارزیابی، واحد سازمانی، پرسنل، وضعیت پرسنل، بازهٔ تاریخ و بازهٔ پایان قرارداد (با میان‌بر «رو به اتمام / منقضی»).
- **خروجی‌ها:** دانلود تک‌تک نمودارها به‌صورت PNG، خروجی Excel از فهرست‌ها (ارزیابی‌ها، پرسنل، کاربران، برنامه‌های بهبود، گزارش رویدادها) و خروجی Excel ترکیبی از گزارش فیلترشده.

### سایر قابلیت‌ها

- **مدیریت پرسنل، کاربران و شاخص‌ها** با جست‌وجو، فیلتر، مرتب‌سازی و صفحه‌بندی.
- **دوره‌های ارزیابی** برای گروه‌بندی و رهگیری پیشرفت هر کمپین.
- **برنامه‌های بهبود** برای نتایج «تمدید مشروط»، با اهداف و پیگیری.
- **کارنامهٔ کارمند** با ثبت رسمی «رؤیت نتیجه».
- **تأیید اصالت سند:** هر کارنامهٔ نهایی یک QR و صفحهٔ عمومی تأیید (بدون احراز هویت) با اثر انگشت SHA-256 دارد.
- **گزارش رویدادها (Audit Log)** برای همهٔ تغییرات حساس.

## شروع سریع با Docker

برای بالا آوردن کل استک (دیتابیس + بک‌اند + فرانت‌اند) با یک دستور:

```bash
docker compose up -d --build
```

- **فرانت‌اند:** `http://localhost:8080` (تنها نقطهٔ ورود از شبکه؛ درخواست‌های `/api/*` را داخلی پروکسی می‌کند)
- **بک‌اند:** `http://localhost:8000` (فقط روی `127.0.0.1`، و به‌عنوان کاربر غیر-root داخل کانتینر)
- **دیتابیس:** پورت `5432` فقط روی `127.0.0.1`

**migration ها:** سرویس جداگانه‌ای به نام `migrate` هست که یک‌بار `alembic upgrade head` را اجرا
می‌کند و بک‌اند تا پایان موفق آن بالا نمی‌آید. این کار عمداً از استارت‌آپ اپ جدا شده: در استقرار
چندنسخه‌ای، اجرای خودکار مایگریشن در بوتِ هر replica یعنی چند پروسه هم‌زمان schema را عوض
می‌کنند. برای اجرای دستی:

```bash
docker compose run --rm migrate
```

> پیش از استقرار واقعی، بخش «استقرار در محیط واقعی» را حتماً بخوانید.

## راه‌اندازی محیط توسعه

### ۱) دیتابیس

ساده‌ترین راه، بالا آوردن فقط سرویس دیتابیس با Docker است:

```bash
docker compose up -d db
```

این کار یک PostgreSQL روی پورت `5432` با کاربر/رمز/دیتابیس `dbspulse` می‌سازد (مطابق `backend/.env.example`). اگر Docker ندارید، هر PostgreSQL 16 محلی با همان مشخصات کافی است؛ فقط `DATABASE_URL` را در فایل `.env` تنظیم کنید.

### ۲) بک‌اند

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate          # ویندوز: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env               # در صورت نیاز مقادیر را ویرایش کنید
alembic upgrade head               # اجرای migration ها + داده‌های اولیه (seed)

# فقط برای محیط توسعه: ساخت کاربران و پرسنل نمونه (جدول «کاربران نمونه» پایین‌تر)
SEED_DEMO_DATA=true alembic upgrade head

uvicorn app.main:app --reload --port 8000
```

بک‌اند روی `http://localhost:8000` بالا می‌آید و مستندات تعاملی API روی `http://localhost:8000/docs` در دسترس است.

**`alembic upgrade head` چه چیزی می‌سازد؟**

- تمام جداول اصلی سامانه (پرسنل، کاربران، دسترسی ارزیابی، شاخص‌ها، رکوردهای ارزیابی، امتیازها، کامنت‌ها، گزارش رویدادها و…)
- شاخص‌های **عمومی** (۱۲ مورد، وزن ۶۰٪) و **تخصصی** (۸ مورد، وزن ۴۰٪) به‌صورت seed
- شماره‌گذار خودکار کد ارزیابی (`EVL-0001`, `EVL-0002`, …)

کاربران و پرسنل نمونه **ساخته نمی‌شوند** مگر این‌که `SEED_DEMO_DATA=true` باشد — پایین‌تر در بخش «کاربران نمونه».

### ۳) فرانت‌اند

```bash
cd frontend
npm install
npm run dev
```

فرانت‌اند روی `http://localhost:5173` بالا می‌آید و درخواست‌های `/api/*` را به‌صورت خودکار به بک‌اند (پورت ۸۰۰۰) پروکسی می‌کند.

## کاربران نمونه

این حساب‌ها **فقط** وقتی ساخته می‌شوند که مایگریشن‌ها با `SEED_DEMO_DATA=true` اجرا شده باشند:

```bash
SEED_DEMO_DATA=true alembic upgrade head
```

رمز مشترکشان در فایل [`backend/app/core/demo_data.py`](backend/app/core/demo_data.py) است.

> ⚠️ این حساب‌ها فقط برای محیط توسعه‌اند و رمزشان در همین مخزن عمومی قابل خواندن است.
> سه گارد جلوی نشتشان به production را می‌گیرند: مایگریشن seed بدون فلگ اصلاً اجرا نمی‌شود؛
> `SEED_DEMO_DATA=true` همراه با `ENVIRONMENT=production` باعث خطای استارت‌آپ می‌شود؛
> و اگر حسابی با این رمز از قبل در دیتابیس مانده باشد، بک‌اند در production بالا نمی‌آید
> (مایگریشن `a1d7f4e9b602` چنین حساب‌هایی را غیرفعال می‌کند).

| نام کاربری | نقش | توضیح |
|---|---|---|
| `hr1` | منابع انسانی | مدیریت پرسنل/کاربران/شاخص‌ها، صف بررسی، داشبورد و گزارش‌های تحلیلی |
| `sup1` | مسئول واحد | ارزیاب «علی محمدی» (P-1001، واحد فروش) |
| `sup2` | مسئول واحد | ارزیاب «زهرا کریمی» (P-1002، واحد فناوری اطلاعات) |
| `dep1` | معاونت | معاونتِ هر سه پرسنل نمونه؛ برای «حسین رضایی» (P-1003) نمره‌دهندهٔ اول هم هست (عنوان شغلی: مدیر) |
| `ceo1` | مدیرعامل | تأییدکنندهٔ نهایی هر سه پرسنل نمونه |

**گردش‌کار کامل (مسیر عادی):** با `sup1` وارد شوید و «علی محمدی» را ارزیابی کنید ← با `hr1` تأیید کنید ← با `dep1` تأیید کنید ← با `ceo1` تأیید نهایی بزنید و خروجی PDF را ببینید.

**مسیر ویژهٔ «مدیر»:** با `dep1` وارد شوید و ارزیابی «حسین رضایی» را مستقیماً شروع کنید.

## اجرای تست‌ها

### بک‌اند (pytest)

تست‌ها منطق حساس پروژه را پوشش می‌دهند: قانون شواهد، محاسبهٔ امتیاز و آستانه‌ها، ماشین حالت گردش‌کار (مسیر عادی و مسیر «مدیر»)، برگشت پرونده، کنترل دسترسی هر نقش و گزارش‌های تحلیلی. هر تست در یک تراکنش/savepoint جدا اجرا و در پایان rollback می‌شود.

```bash
cd backend
source .venv/bin/activate
pip install -r requirements-dev.txt

# ساخت دیتابیس تست (فقط یک‌بار لازم است)
psql -h localhost -U dbspulse -c "CREATE DATABASE dbspulse_test OWNER dbspulse;"

ruff check .
pytest -v
```

### فرانت‌اند

```bash
cd frontend
npm run lint      # oxlint
npm test          # Vitest
npm run build     # بررسی نوع (tsc) + build تولیدی
```

> همهٔ این بررسی‌ها روی هر push/PR به‌صورت خودکار در GitHub Actions اجرا می‌شوند (`.github/workflows/ci.yml`).

## خروجی PDF و وابستگی‌های سیستمی

خروجی PDF کارنامهٔ نهایی با **WeasyPrint** ساخته می‌شود که به چند کتابخانهٔ سیستمی (نه پکیج پایتون) نیاز دارد. اگر این کتابخانه‌ها نصب نباشند، بقیهٔ برنامه سالم کار می‌کند و فقط دکمهٔ «چاپ / خروجی PDF» با پیام واضح خطا برمی‌گردد.

- **با Docker:** نیازی به کار اضافه نیست؛ `backend/Dockerfile` این کتابخانه‌ها را نصب می‌کند.
- **Linux (Debian/Ubuntu):**
  ```bash
  sudo apt-get install -y libpango-1.0-0 libpangocairo-1.0-0 libpangoft2-1.0-0 \
      libharfbuzz0b libcairo2 libgdk-pixbuf-2.0-0 libffi8 shared-mime-info fonts-liberation
  ```
- **macOS:** `brew install pango gdk-pixbuf libffi`
- **Windows:** نصب کتابخانه‌های بومی GTK دشوار است؛ ساده‌ترین راه، اجرای بک‌اند داخل Docker یا WSL است.

> فونت Vazirmatn برای رندر فارسی در `backend/app/templates/fonts/` قرار دارد و قالب آن را از مسیر محلی بارگذاری می‌کند؛ نیازی به فونت سیستمی نیست.

## استقرار در محیط واقعی

نقطهٔ شروع، فایل [`.env.production.example`](./.env.production.example) است:

```bash
cp .env.production.example .env    # کنار همین docker-compose.yml
# مقادیر خالی را پر کنید، بعد:
docker compose up -d --build
```

برنامه در حالت `ENVIRONMENT=production` عمداً **fail-closed** است — یعنی به‌جای اجرا شدن
با یک پیکربندی توسعه‌ای، با خطای صریح بالا نمی‌آید. گاردهای فعال:

| اگر این اشتباه باشد | چه اتفاقی می‌افتد |
|---|---|
| `JWT_SECRET_KEY` روی مقدار پیش‌فرض دمو | استارت‌آپ fail می‌شود |
| `CORS_ORIGINS` شامل localhost یا بدون https | استارت‌آپ fail می‌شود |
| `PUBLIC_BASE_URL` روی localhost یا بدون https | استارت‌آپ fail می‌شود |
| `SEED_DEMO_DATA=true` | استارت‌آپ fail می‌شود |
| `FORWARDED_ALLOW_IPS=*` | استارت‌آپ fail می‌شود |
| حساب دموی فعالی با رمز منتشرشده در دیتابیس مانده باشد | استارت‌آپ fail می‌شود |

علاوه بر این:

1. یک لایهٔ **HTTPS / reverse proxy** جلوی سرویس `frontend` (پورت ۸۰۸۰) قرار دهید — نمونهٔ پیکربندی Nginx + Certbot در [`deploy/nginx-https.conf.example`](./deploy/nginx-https.conf.example) موجود است.
2. **`FORWARDED_ALLOW_IPS`** را به IP/شبکهٔ پروکسی محدود کنید؛ با `*` هر کلاینتی می‌تواند هدر `X-Forwarded-For` جعلی بفرستد و محدودیت نرخ ورود را دور بزند.
3. **`ENABLE_SCHEDULER`** فقط روی یک instance روشن شود — زمان‌بند درون‌پروسه است و با چند replica اعلان تکراری می‌سازد.
4. کاربر ادمین واقعی را خودتان بسازید؛ حساب‌های دمو در production اصلاً ساخته نمی‌شوند.

## ملاحظات امنیتی

- تمام endpoint های تغییردهندهٔ داده پشت بررسی نقش در بک‌اند قفل‌اند، نه صرفاً با مخفی‌کردن دکمه در UI.
- دسترسی به هر رکورد ارزیابی یا پرسنل، علاوه بر نقش پایه، بر اساس `evaluation_access` نیز بررسی می‌شود.
- رمز عبور با **Argon2** هش می‌شود.
- ورود (`/api/auth/login`) دو لایه دفاع دارد: **۱۰ تلاش در دقیقه به ازای هر IP**، و **قفل حساب** پس از ۵ تلاش ناموفق روی یک نام کاربری (۱۵ دقیقه). لایهٔ دوم لازم است چون محدودیت per-IP یک حملهٔ توزیع‌شده و آهسته روی یک حساب مشخص را نمی‌بیند. قفل در دیتابیس ثبت می‌شود (نه حافظهٔ پروسه)، در گزارش رویدادها می‌آید و به منابع انسانی اعلان می‌دهد. در پنجرهٔ قفل، حتی رمز درست هم پذیرفته نمی‌شود.
- nginx مقدار `X-Forwarded-For` را **بازنویسی** می‌کند (نه اضافه‌کردن به زنجیره)، تا کلاینت نتواند با هدر جعلی، آدرسی را که محدودیت نرخ روی آن کلید می‌خورد عوض کند.
- در حالت `ENVIRONMENT=production` مستندات Swagger (`/docs` و `/openapi.json`) غیرفعال می‌شوند.
- تغییر رمز یک کاربر توسط منابع انسانی، بلافاصله تمام نشست‌های (access/refresh) قبلی همان کاربر را باطل می‌کند.
- صفحهٔ عمومی تأیید اصالت با **توکن تصادفی** کار می‌کند (نه کد ترتیبی ارزیابی) تا قابل شمارش و استخراج انبوه نباشد.
